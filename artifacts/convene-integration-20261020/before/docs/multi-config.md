# 多套配置、共享声骸与官方批量导入（2026-10-20）

本次基于现有工作台扩充，不改变评分公式或整体五卡布局。正式代码入口为 `js/multi-config.js`、`js/multi-config-browser.js`；数据仍放在原 `mcData`，不是并行存档系统。详尽交接及实际验收证据见本次完整源码包中的 `handoff/`。

## 数据归属

| 数据 | 权威位置 | 语义 |
|---|---|---|
| 角色身份／来源 | `roleId`、`roleListId`、`importSource`、`gameRoleId` | 本地身份与官方账号／游戏角色身份分离 |
| 等级、共鸣链、官方武器／技能 | 角色记录 | 角色级，不随配置复制；完整覆盖按最新官方值重建 |
| 配置 | `role.configurations[]` | 稳定UUID、roleId、name、五槽ID引用、settings、时间与source |
| 评分设置 | `configuration.settings` | damageMode、extraEnergy、referenceHealth；不盲目复制角色其他字段 |
| 默认／当前配置 | `defaultConfigurationId`、`activeConfigurationId` | 普通角色入口采用默认配置；带configuration参数可进入指定配置 |
| 声骸实体 | 根 `echoes[]` | 唯一costId；共享使用同一份实体。复制配置只复制引用 |
| 当前五槽 | `role.costList` | 由当前配置生成的兼容投影；中间空槽保持位置，尾部空槽裁去 |
| Classic未使用库 | `unusedEchoes` | 未被任何配置引用的实体投影；Register库显示全部echoes |
| 收藏与其他声骸元数据 | `wuwa.register.echoMeta.v1[costId]` | 全局实体状态，完整覆盖角色不清空它 |
| 配置草稿 | `wuwa.echoTool.drafts.v1` | baseline.role.configurationId明确归属；来源指纹只包含当前角色投影 |
| 采纳／旧名称 | `wuwa.echoTool.localConfigurations.v1`、`wuwa.register.names.v1` | 既有协议保留；新配置名称以configuration.name为准 |

原代码没有独立的角色备注／养成状态编辑器；完整度与养成统计主要由声骸、分数与角色数据推导。迁移仍保留旧角色上所有未知备注／标记字段；完整覆盖从本次官方fresh角色重建，所以这些角色专属字段被移除／恢复默认。声骸元数据中的额外字段仍作为全局数据保留，不以相似内容推断所属角色。

## 无损迁移

`loadoutVersion:2`标识新格式；旧记录生成第一套配置，保留角色ID、正常唯一costId、角色字段及原名称。再次运行不会重复生成配置。旧重复costId不能证明是同一物件，后出现的实体分配新UUID并保留legacyCostId；对应全局元数据按旧键复制，避免丢失。无法可靠恢复的历史歧义草稿保留并要求重新比较。

旧草稿绑定到迁移后的第一套配置，只有原本有效的采纳签名才随绑定更新，不把失效签名自动修复成有效。旧备份外层协议仍可读取；新备份在原core section中保存完整新格式、实体、全部配置与引用。缺失引用显示空槽与警告，不猜测引用其他实体。

## 官方导入

现有`phantomPropId`无法由代码证明是稳定单件实例ID，且用于目录类型转换，不能作为跨角色合并依据。官方再次导入采用新实例；不按名字、Cost或词条相似度合并。旧实体安全保留，即使失去引用也进入未使用库，不自动当垃圾删除。

已有角色默认维持现有，不请求其详情，也不更新其任何已保存角色／配置／声骸数据。批量保留／覆盖只作用于已选择且已存在的角色；每页6位，选择跨页保留。覆盖前要完成所有新增／覆盖项预览校验并勾选重置范围确认；失败项目未完成时不允许提交成功项目的半批次。

完整覆盖保留本地roleId以保护外部角色链接，但重建该角色记录、官方一套配置及评分缓存，删除其全部旧配置、基线／草稿／采纳与旧名称，清理相关会话恢复缓存。其他角色的配置与全局声骸收藏不变；保留项逐字节不改。

## 提交与相容性

核心事务先读取快照，内存构建、校验并检查来源，再写入。跨核心／草稿／采纳／名称／实体元数据的提交带持久化回滚日志`wuwa.multiconfig.transaction.v2`；写入失败回滚，下次Register启动恢复未完成事务。官方批量提交在可用环境额外使用Web Locks。

localStorage不是数据库原生事务。日志、同步提交和乐观检查不能宣称所有跨进程时序都具有数据库隔离性；恢复失败会保留日志并显示错误，不自动清空存档。应避免多个旧版／新版页面并发写入；真正的数据库级跨页事务需要后续统一异步存储架构，本次没有伪装成原生原子性。

Classic读取当前配置的兼容投影，原评分和刷新入口保留。旧版编辑写回当前配置／共享实体；共享真实字段变更也提示影响范围。Classic原刷新更新当前配置，不等同Register的明确“完整覆盖”；需要重置全部配置时使用新的批量确认页。这是在保留旧流程行为与新覆盖语义之间的明确边界。
